# Architecture

## Stack

- TypeScript
- React
- Vite
- Node/Express
- PostgreSQL
- pgvector
- OpenAI-compatible APIs
- Docker Compose
- Nginx
- Smallstep CLI for local development certificates

## Docker Topology

The Docker app entrypoint is `https://localhost:8787`.

```text
browser -> nginx:443/TLS -> app-1:8787 / app-2:8787 -> postgres:5432
```

- `nginx` is the only public service.
- `nginx` load balances to `app-1` and `app-2` on the private Compose network.
- Public Docker traffic must be HTTPS only.
- App containers and PostgreSQL stay internal to Docker Compose.
- Local TLS certificates are generated by the `cert-init` Smallstep CLI service into ignored `data/tls/`.
- Docker sets `APP_INSTANCE_URLS` to probe `app-1` and `app-2`; instance health must stay free of secrets.
- Nginx sets `X-Real-IP` and `X-Forwarded-For` to its own `$remote_addr`, overwriting any client-supplied values. It listens on 443 only.
- The app reads `X-Forwarded-For` only when the socket peer is in `TRUSTED_PROXIES`. Behind Docker, that peer is the Nginx container, so `TRUSTED_PROXIES` must cover the Compose network subnet (see `.env.example`). Otherwise `IP_ALLOWLIST` and `IP_DENYLIST` judge every request by the Nginx address.

## IP Filtering

Purpose: an optional, role-agnostic access control layer that admits or refuses clients by IP address before any route runs. It is configured entirely by environment variables and is off when both lists are blank.

| Variable | Meaning |
| --- | --- |
| `IP_ALLOWLIST` | Comma-separated IPv4/IPv6 addresses or CIDR ranges. When non-empty, only listed clients are admitted. |
| `IP_DENYLIST` | Comma-separated IPv4/IPv6 addresses or CIDR ranges. Matching clients are refused. |
| `TRUSTED_PROXIES` | Comma-separated addresses or CIDR ranges of proxies whose `X-Forwarded-For` is honoured. |

- Values are validated at startup. An empty entry or an invalid entry stops the server and names the variable. The full list is never echoed.
- Precedence: the denylist is checked first and always wins. An empty allowlist admits every client that is not denied. A non-empty allowlist admits only listed clients.
- The filter is one Express middleware, mounted before CORS and body parsing. `/api/health` and `/api/instance-health` are exempt so container probes keep working.
- A refused request gets `403` with `{"error":"Forbidden."}`. The client address is not echoed or logged.
- Fail closed: if a client address cannot be resolved while any rule exists, the request is refused.

### Client Address Resolution and Proxy Trust

- The socket peer is trusted as a proxy only when it is in `TRUSTED_PROXIES`. Only then is `X-Forwarded-For` read.
- The header is walked from the right, skipping trusted proxy hops. The first untrusted hop is the client. Entries to its left were supplied by the client and are ignored.
- Behind the bundled Docker Nginx, the socket peer is the Nginx container. Nginx overwrites `X-Forwarded-For` with its own `$remote_addr`, so the app sees the real client only through that hop. `TRUSTED_PROXIES` must cover the Compose network, which is not pinned, so the operator sets it to the subnet reported by `docker network inspect roos_default`.
- Blank `TRUSTED_PROXIES` trusts no proxy. Behind Nginx this means every request is judged by the Nginx address.
- Security caveat: the filter is only as trustworthy as the configured proxy chain. Do not list a range that contains clients, because they could then forge `X-Forwarded-For` and bypass the rules.

### Example Configurations

```text
# Admit only an office range and one VPN host (Docker: trust the Compose subnet)
IP_ALLOWLIST=203.0.113.0/24,198.51.100.7
IP_DENYLIST=
TRUSTED_PROXIES=172.20.0.0/16

# Block one client, admit everyone else
IP_ALLOWLIST=
IP_DENYLIST=192.0.2.44

# IPv6 allowlist with a denylist exception inside it
IP_ALLOWLIST=2001:db8::/32
IP_DENYLIST=2001:db8:0:1::/64
```

## Provider Configuration

- LM Studio embeddings are expected at host URL `http://127.0.0.1:1234`.
- Docker reaches LM Studio through `http://host.docker.internal:1234/v1`.
- Default embedding model: `text-embedding-nomic-embed-text-v1.5-embedding`.
- Default embedding dimensions: `768`.
- OpenAI-compatible local providers can use `not-needed` as the API key.
- If the LLM provider does not support the Responses API, set `LLM_API_STYLE=chat`.

## Data Stores

- PostgreSQL is the source of truth for users, sessions, jobs, job postings, resume versions, analysis metadata, and embeddings.
- pgvector is used for embedding storage and matching.
- `jobs.analysis_kind` separates user-visible applications from admin-only candidate assessments.
- Standard users only see `application` jobs. Admins can see `candidate_assessment` rows and may convert them to applications.
- `user_match_profiles` stores one searchable semantic profile per user, built from the latest resume plus application and analysis context.
- Admin semantic user profiles use `vector(768)` for `text-embedding-nomic-embed-text-v1.5-embedding`; changing embedding dimensions requires a matching schema migration and index rebuild.
- Admin user search embeds the search phrase, queries `match_user_match_profiles(...)`, and ranks matching users through a pgvector IVFFlat index while preserving exact text search as fallback. Text relevance ranks exact profile, title, skill, and evidence matches ahead of broad semantic matches.
- `job_posting_match_profiles` stores one searchable semantic profile per job posting, built from the title, skill tags, and description.
- Job search embeds the search phrase, queries `match_job_posting_match_profiles(...)`, and ranks matching postings through a pgvector IVFFlat index while preserving exact title, description, and skill search as fallback.
- Analysis cache entries are stored in PostgreSQL.
- The app connects with the restricted `APP_DB_USER`; it must not connect as the Postgres superuser.

## SQL Organization

- SQL lives under `sql/`, not inline TypeScript business logic.
- Migrations live in `sql/migrations/`.
- Query files are grouped by domain:
  - `sql/jobs/`
  - `sql/job_postings/`
  - `sql/job_posting_match_profiles/`
  - `sql/users/`

  - `sql/resume_versions/`
  - `sql/resume_chunks/`
  - `sql/user_match_profiles/`
  - `sql/analysis_cache/`
  - `sql/admin/`

## Analysis Flow

1. Extract resume text from upload.
2. Redact the authenticated user's profile name and email plus user-confirmed phone, address, and personal link values.
3. Replace persisted upload filenames with neutral names that preserve only the extension.
4. Store redacted profile resume text plus the original uploaded file bytes for authorized same-format downloads.
5. Chunk redacted resume text.
6. Create embeddings for the job query and redacted resume chunks.
7. Store redacted resume chunk embeddings in PostgreSQL with pgvector.
8. Rank evidence chunks using vector similarity.
9. Ask the LLM for structured HR assessment fields using redacted evidence and redacted resume text.
10. Compute final fit score and fit level deterministically in the server.
11. Persist job result, analysis JSON, recommendation, models, and chunk count.

## Admin Candidate Assessment Flow

1. Admin opens a job posting from the Jobs page and chooses **Assess a candidate**.
2. The UI opens a candidate picker backed by `/api/admin/users`.
3. Candidate search is filtered to exclude users already assessed for the selected posting.
4. `/api/admin/users/:userId/analyze/latest` analyzes the candidate's latest stored resume and creates a `candidate_assessment` job.
5. Candidate assessment rows are visible to admins but are filtered out of standard user application lists, profile views, and user-facing search.
6. `/api/admin/jobs/:jobId/convert-to-application` changes the assessment to an application when an admin decides it should become part of application history.

## Pagination Flow

- Page-facing list endpoints accept `limit` and `offset`.
- The React UI requests 10 records per page.
- Scroll sentinels use `IntersectionObserver` to append the next page when the user nears the bottom of a list.
- Appending de-duplicates entities by `id` so a refresh or overlapping fetch does not duplicate rows.
- The UI treats a page smaller than the requested limit as the end of the list.
- Paginated endpoints include:
  - `/api/jobs`
  - `/api/applications`
  - `/api/job-postings`
  - `/api/admin/users`
  - `/api/admin/job-postings/:jobPostingId/applications`

Semantic search pagination asks the vector matcher for `offset + limit` candidate ids, then applies SQL `LIMIT/OFFSET`. This keeps later pages stable while still allowing text relevance and database filters to participate in final ordering.

## Theme Flow

- Themes are CSS-variable sets in `src/client/styles.css`.
- The active theme name is stored in browser local storage as `roos-theme`.
- The React app applies the theme by setting `document.documentElement.dataset.theme`.
- `launch` removes the `data-theme` attribute and uses the default `:root` variables.
- `icy-blue` and `crimson-lit` use `:root[data-theme="..."]` overrides.
- The header theme button cycles through `Launch`, `Icy Blue`, and `Crimson Lit`.

## Resume Download Flow

- Versioned profile resume uploads persist file bytes, content type, file size, neutral filename, and redacted extracted text.
- `/api/resumes/:resumeId/download` requires authentication.
- Standard users can download only their own resume versions.
- Admins can download user resume versions from the admin users page.
- The download response uses the stored content type and a neutral versioned filename such as `resume-v2.pdf`.

## Health Flow

- `/api/health` is a lightweight public health endpoint used by app/container readiness and the login banner.
- `/api/instance-health` reports private per-instance process status for server-side probes.
- `/api/admin/system-health` aggregates storage, provider config, and all configured app instances.
- `/api/admin/system-health` requires authenticated admin access.
